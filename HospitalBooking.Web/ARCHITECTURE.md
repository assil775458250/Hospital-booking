# معمارية مشروع بوابة المدير - نظام يُسر (Yusr Admin Architecture)

دليل التوثيق المعماري الرسمي لبوابة الإدارة والتحكم في نظام **يُسر** لإدارة حجز المواعيد الطبية.

---

## 1. الفلسفة المعمارية ونمط التصميم

يعتمد المشروع على تكامل منهجي بين ثلاثة مبادئ معمارية أساسية:
1. **نمط MVVM (Model-View-ViewModel):** لفصل منطق العرض وإدارة الحالة عن واجهة المستخدم والاتصال بالخادم.
2. **تنظيم الميزات (Feature Organization):** هيكلة متسقة وموحدة عبر كافة الوحدات الوظيفية للنظام.
3. **فصل المسؤوليات (Separation of Concerns):** وضع حدود صارمة تمنع تداخل المهام بين الطبقات البرمجية المختلفة.

```
┌────────────────────────────────────────────────────────────────────────┐
│                                 VIEW                                   │
│  (HTML Template + CSS Styles + Lightweight Standalone Component TS)    │
└───────────────────────────────────▲────────────────────────────────────┘
                                    │ Two-way bindings / Events / Signals
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│                              VIEWMODEL                                 │
│  (UI State Management, User Interaction Logic, Presentation Data)      │
└───────────────────────────────────▲────────────────────────────────────┘
                                    │ Service Invocations
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│                               SERVICE                                  │
│  (HTTP Requests, API Integration, Error Handling, Data Fetching)       │
└───────────────────────────────────▲────────────────────────────────────┘
                                    │ Strongly-Typed DTOs
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│                                MODEL                                   │
│  (Interfaces, Types, Enums, API Request/Response DTOs)                 │
└────────────────────────────────────────────────────────────────────────┘
```

## 3. تفصيل مسؤوليات المجلدات الرئيسية

### أ. مجلد `core/` (البنية التحتية المركزية)
* **المسؤولية:** يحتوي على الخدمات والمكونات التي تخدم دورة حياة التطبيق بأكمله (Application-wide Singletons).
* **الأقسام الفرعية:**
  * `auth/`: إدارة التوكن (JWT)، حالة تسجيل الدخول العامة، والتخزين المحلي الآمن للجلسة.
  * `guards/`: حراس التوجيه لمنع الوصول غير المصرح به (`AuthGuard`, `RoleGuard`).
  * `interceptors/`: اعتراض طلبات واستجابات HTTP لإضافة التوكن، معالجة أخطاء الشبكة العامة، وإدارة مؤشرات التحميل.
  * `config/`: تكوين بيئة العمل (App Config, Endpoints, Constants).

### ب. مجلد `shared/` (العناصر المشتركة)
* **المسؤولية:** تجميع العناصر القابلة لإعادة الاستخدام في أي واجهة دون الاعتماد على ميزة (Feature) محددة.
* **الأقسام الفرعية:**
  * `components/`: أزرار مخصصة، جداول عامة، نوافذ منبثقة، بطاقات عرض.
  * `directives/`: توجيهات سلوكية (مثل: منع التكرار، التنسيق التلقائي للمدخلات).
  * `pipes/`: تحويل التواريخ الهجرية/الميلادية، العملات، صيغ أرقام الهواتف.
  * `utilities/`: دوال حسابية، معالجة المصفوفات، التحقق من صحة المدخلات المشتركة.

### ج. مجلد `models/` (نماذج البيانات والأنواع)
* **المسؤولية:** تعريف بنية البيانات باستخدام TypeScript Interfaces وTypes وEnums.
* **الضوابط:**
  * لا يحتوي هذا المجلد على أي كود تنفيذي أو منطق برمجي.
  * يحدد شكل طلبات واستجابات الـ API بدقة (Strict Typing).

### د. مجلد `views/` (واجهات العرض)
* **المسؤولية:** تمثيل كل صفحة أو جزء مرئي من التطبيق.
* **الضوابط:**
  * تطبيق أسلوب المكونات المنفصلة (Separate Component Files: `.ts`, `.html`, `.css`).
  * ملف TypeScript يكون خفيفًا جدًا (`Thin Component`) ودوره ربط قالب الـ HTML بالـ ViewModel المقابل فقط.
  * لا يحتوي إطلاقًا على منطق أعمال (Business Logic) أو طلبات شبكة (HTTP Requests).

### هـ. مجلد `viewmodels/` (إدارة حالة الصفحة ومنطق الواجهة)
* **المسؤولية:** تمثيل "عقل" الواجهة؛ يحمل حالة الصفحة، يتعامل مع نقرات المستخدم وأحداث النماذج، ويستدعي طبقة الخدمات.
* **الضوابط:**
  * لا يتعامل مع الـ DOM أو عناصر HTML مباشرة.
  * يستخدم Angular Signals أو Observables لبث التغييرات للـ View.
  * معزول عن تفاصيل الـ HTTP ويحصل على البيانات جاهزة من الخدمات.

### و. مجلد `services/` (خدمات البيانات والاتصال بالخادم)
* **المسؤولية:** تنفيذ طلبات HTTP الموجهة لنقاط نهاية الـ REST API الخاصة بنظام يُسر.
* **الضوابط:**
  * يعتمد على `HttpClient` لإرسال واستقبال البيانات.
  * يتعامل مع النماذج المعرفة في مجلد `models/` فقط.
  * لا يحتفظ بحالة الواجهة (UI State) ولا يرتبط بأي صفحة محددة.

## 4. تطبيق مبادئ MVVM في Angular

| العنصر | التقنية المستخدمة | المسؤولية | الممنوعات |
| :--- | :--- | :--- | :--- |
| **Model** | TypeScript Interfaces / Types | تعريف شكل البيانات والعقود مع الـ API | يُمنع احتواؤه على منطق تنفيذي أو استدعاءات |
| **View** | Standalone Component (HTML + CSS + TS) | عرض البيانات والتقاط تفاعل المستخدم وتمريره للـ ViewModel | يُمنع احتواؤه على منطق معقد أو استدعاء HTTP |
| **ViewModel** | Angular Injectable Class | إدارة الحالة وتنسيق البيانات للعرض والتفاعل مع المستخدم | يُمنع الوصول المباشر للـ DOM أو تنفيذ طلبات HTTP مباشرة |
| **Service** | Angular Injectable (`providedIn: 'root'`) | الاتصال بالـ Backend والتعامل مع بروتوكول HTTP | يُمنع تخزين حالة العرض أو ربطه بالواجهات |

## 5. قواعد تسمية الملفات (Naming Conventions)

نلتزم بنمط التسمية التقليدي والواضح الذي يفصل الوظائف:

1. **مكونات الواجهة (Views):**
   * كود المكون: `<feature-name>.component.ts`
   * قالب المكون: `<feature-name>.component.html`
   * تنسيق المكون: `<feature-name>.component.css`
   * اختبار المكون: `<feature-name>.component.spec.ts`

2. **نماذج العرض (ViewModels):**
   * كود الـ ViewModel: `<feature-name>.viewmodel.ts`
   * اختبار الـ ViewModel: `<feature-name>.viewmodel.spec.ts`

3. **خدمات الاتصال (Services):**
   * كود الخدمة: `<feature-name>.service.ts`
   * اختبار الخدمة: `<feature-name>.service.spec.ts`

4. **النماذج والعقود (Models):**
   * النموذج الأساسي: `<feature-name>.model.ts`
   * نماذج الطلبات/الاستجابات: `<feature-name>-request.model.ts` / `<feature-name>-response.model.ts`

5. **البنية المشتركة والمركزية:**
   * الحراس: `<name>.guard.ts`
   * المعترضات: `<name>.interceptor.ts`
   * التوجيهات: `<name>.directive.ts`
   * الأنابيب: `<name>.pipe.ts`

## 6. قواعد تنظيم كل ميزة (Feature Organization)

لكل ميزة في بوابة المدير (مثل `doctors` أو `appointments`)، يتم بناء مسار متناغم ومتطابق عبر جميع الطبقات:
* `src/app/models/admin/doctors/`
* `src/app/views/admin/doctors/`
* `src/app/viewmodels/admin/doctors/`
* `src/app/services/admin/doctors/`

هذا التناغم يضمن:
1. سهولة الاستدلال وسرعة الوصول لأي ملف مرتبط بالميزة.
2. عزل الميزات عن بعضها لمنع التداخل والاعتماديات المتشابكة.
3. استقلالية تامة بين بوابة المدير (`admin`) وبوابة الطبيب (`doctor`).

---

## 7. ضوابط ومعايير الجودة الصارمة

1. **الاستقلالية التامة (Loose Coupling):** لا تعتمد الطبقات السفلية (Model, Service) على الطبقات العليا (ViewModel, View).
2. **استخدام المكونات المستقلة (Standalone Components):** جميع المكونات المستقبلية تكون Standalone بدون استخدام NgModules.
3. **الالتزام بالنمط الصارم (TypeScript Strict Mode):** تعريف الأنواع بدقة وتجنب استخدام `any`.
4. **عدم إنشاء ملفات فارغة دون حاجة:** تُنشأ ملفات الكود فقط عند بدء تنفيذ الميزة وظيفياً.
